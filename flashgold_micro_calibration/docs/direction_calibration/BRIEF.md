## 1. The order-flow feed in the EA and in the replay

- 1. The feed is five live numbers read at ONE place. ScoreOrderFlow (SpeedAlert_FlashGold_Micro.mq5:2463-2493) reads terminal globals XPW_XAU_OK, _HEARTBEAT, _FORCE_IMB, _NEAR_IMB, _BOOK_IMB on every direction-decision tick. VWAP_VALID, VWAP_PRICE and LIVE_FEEDS are read only by ReadMasterVwapTelemetry (2515-2553), whose single call site (5058, inside SarOrderFlowDecisionLog) only fills SAR_OrderFlowDecision_v2.csv: the master VWAP never changes a decision. A simulator only has to supply, per quote tick, OK, a fresh HEARTBEAT and three signed numbers. The flow code is byte-identical in the live parent: the Micro file differs from PARENT_EA_SOURCE.txt in exactly 4 hunks (version, TradingEnabled default true->false, tester-only OnInit guard 1105-1107, FlashGoldCaptureMicroQuote() at 1163); basis/parent.mq5 differs from PARENT_EA_SOURCE.txt only in version/description. Parent file says #property version 1.499, ORIGIN.json says parent_version 1.500.
- 2. Exact vote/score arithmetic. A feature with |value| >= MinFlowImbalance 5.0 casts one vote (value>0 buy, else sell) and adds FlowComponentScore 1.0 to that side; flowDir = +1/-1 only when >= 2 of the 3 votes agree. Side score = 0.5 (spread ok) + 1.0 (speed side) + 1.5 (M1 body >= 21 pts) + 1.5 (10 s micro-break by 3 pts) + 1.0 per vote; winner needs >= 4.0 and a lead >= 1.5. No feed: max 4.5, so the ONLY winning pattern is speed+body+micro all agreeing. With feed (speed fixed, 3 body x 3 micro x 27 vote assignments = 243 combos, decision_table.py): 87 give a winner on the speed side (speed + body-or-micro + 1 vote wins; speed + 3 votes wins alone), 32 give a winner AGAINST the speed direction (e.g. body and micro both against speed + 1 vote), 124 none. So flow can create entries the neutral logic never takes and can flip the side.
- 3. The market route (FOLM, 74% of real trades) is controlled by flow. DecideAction (2742-2767) goes market only if speedDir==winner and follow21/37 and MarketEntryAllowedByFlow (2770-2789): flow agrees (flowDir==winner) allows it with no further test; neutral or disagreeing flow needs body AND micro with the winner, score >= 5.0 and lead >= 2.0; a SELL with neutral flow is always downgraded to a stop. Neutral max is 4.5 < 5.0, so without a feed the market route can never fire. Verified: replay of the shipped preset, Oct 2026 (my instrumented run), 586 trades, 0 market (FLXQ 464, EXHL 122). Opening it (WeakFlowMarketMinScore 4.5, DowngradeNeutralSellMarketToStop 0) makes 1,207 of 1,329 trades FOLM and FLXQ vanishes, because every neutral winner tick has follow-through (98,733 of 98,733).
- 4. Flow matters for ENTRY only. BuildDirectionState runs on every tick while a speed alert is active (OnTick 1198; no winner = SKIP and try again next tick; alert lasts SpeedAlertHoldSeconds 20 s from the start of the 10 s lookback window, 2077/2164) and the first passing tick wins. With InpUseEntryHold (true, 1100 ms) the DirectionState is frozen at the arm tick (1781, 1807, 1856, 1874) and the result is written into the order comment as :FA/:FD (3140-3141). Exits read that comment, never live flow, and both flow-reading exits (TryPreSpeedAgainstDefenseClose 10888, TryStopFlowDisagreeDangerClose 11218) are inside ValidatePosition behind the 6.8-pip release gate (9461, 9519-9521, 12195); the first is also dead once the trade hit +21 (10894). The real chart has 0 exit comments SA_STOP_FLOW_DANGER or SA_PRE_SPEED_DEFENSE in 2,584 trades. All V45/V48/V451/V452/V461/AI-journal consumers are telemetry or shadow scorecards without execution authority. For direction calibration only ScoreOrderFlow -> score -> WinnerSide -> route matters.

### Vote and score arithmetic

ScoreOrderFlow (SpeedAlert_FlashGold_Micro.mq5:2463-2493), called from BuildDirectionState (2341) on every tick while a speed alert is active. (0) UseOrderFlow false or empty FlowGVPrefix: return (neutral). (1) GlobalVariableCheck of OK and HEARTBEAT, else return. (2) GlobalVariableGet(OK) < 0.5: return. (3) age = GetTickCount64() - HEARTBEAT; age > MaxFlowAgeMs (4000): return (negative age passes). (4) flowFresh = true; forceImb/nearImb/bookImb = GV() (0.0 if the variable is missing). (5) AddFlowVote x3 (force, near, book; 2556-2570): |v| < MinFlowImbalance (5.0) casts nothing; v > 0.0 is a buy vote and buyScore += FlowComponentScore (1.0); anything else (v <= -5, and NaN, because the comparison falls through) is a sell vote and sellScore += 1.0. (6) flowDir = +1 if buyVotes >= 2, -1 if sellVotes >= 2, else 0: a single vote or a 1-1 split leaves flowDir 0 but the +1.0 stays in the scores. Per-side score (BuildDirectionState 2322-2365, defaults equal to the shipped preset) = 0.5 SpreadStableScore on BOTH sides if spread <= MaxSpreadPoints 31 + 1.0 SpeedDirectionScore for the speedDir side + 1.5 CandleBodyScore if the forming M1 body >= 21 points in that direction + 1.5 MicroBreakScore if mid breaks the 10 s high/low by 3 points + 1.0 per flow vote: max 7.5 with feed, 4.5 without. WinnerSide (2639-2646): the side with score >= MinDirectionScore 4.0 and lead >= MinScoreEdge 1.5, else 0. flowAgreesWithWinner = (winner != 0 && flowDir == winner), flowDisagreesWithWinner = (winner != 0 && flowDir == -winner) (2345-2346): the labels are relative to the winner side, not to the order side (an EXHL limit fades the burst, so FA there means flow agrees with the burst). Decision table with speed fixed at +1 and spread ok (243 = 3 body x 3 micro x 27 vote assignments, decision_table.py): without votes only body+micro+speed winning (4.5); with votes 87 combos give a buy winner (min votes: 0 if body and micro both agree, 1 if speed plus one of body/micro agree, 3 if speed stands alone), 32 combos give a SELL winner against the speed (body and micro both against speed + >= 1 sell vote scores 4.5 vs 1.5), 124 give no winner. A buy winner with follow-through (speed side): flowDir +1 -> market always allowed (38 combos); flowDir 0 -> market allowed in 9 of 37; flowDir -1 -> 3 of 12; without feed -> never.

SpeedAlert_FlashGold_Micro.mq5 refuses to initialise outside the Strategy Tester (OnInit 1105-1107: INIT_FAILED unless MQLInfoInteger(MQL_TESTER)); TradingEnabled defaults to false and all shipped presets are *_DISABLED (the REPORT says TradingEnabled must be switched on in the tester). In a tester run GlobalVariableCheck(XPW_XAU_OK/HEARTBEAT) is false (REPORT section 12 and tools/classify_inputs.py state the feed does not exist in the tester; my recollection of the MQL5 documentation is that the tester agent has its own, initially empty, global-variable store, which I could not verify offline), so ScoreOrderFlow returns at line 2469-2470 every tick: flowFresh=false, flowDir=0, forceImb=nearImb=bookImb=0.0, flowAgrees/Disagrees=false, no :FA/:FD in comments, scores max 4.5, market route impossible (WeakFlowMarketMinScore 5.0), SELL market always stop, no flow exits, telemetry columns flow_fresh=false and master_vwap_degraded=true. This equals UseOrderFlow=false (which the calibrated presets ship). Consequences for injecting a simulated feed into a tester run: (1) the globals would have to be written inside the tester process (companion indicator/EA or a code change in ScoreOrderFlow reading a file by tick time_msc); (2) HEARTBEAT is tested against GetTickCount64() (wall clock, not simulated time; the EA's own continuation filter notes tester time is simulated and avoids GetTickCount64 in the tester), so HEARTBEAT must be rewritten on every tick or the age test avoided; staleness/outages must be simulated by deleting the globals or setting OK=0, not by letting the heartbeat age; (3) the writer must run before the EA's OnTick on each tick (ordering unverified); (4) execution delay and 'every tick based on real ticks' still matter (REPORT section 10).

## 2. The direction logic and its inputs

- WHICH SIDE. Without the order-flow feed (replay, Strategy Tester, and the calibrated preset, which sets UseOrderFlow=false) the traded side is ALWAYS the side of the 10-second speed alert. At the shipped weights (spread-stable 0.5, speed 1.0, body 1.5, micro-break 1.5; winner needs score >= 4.0 and lead >= 1.5) only 2 of the 18 (speed, body, micro) states give a winner: speed+body+micro all agreeing (4.5 vs 0.5); MinScoreEdge is dead for any value 0.5-4.0. Trading against the burst needs EntryRouterMode >= 2 (limit-order fade on a wick/snapback/opposite-pressure flag, taken even with no winner) or 2-3 live flow votes against it (13 of 90 flow states per alert direction produce an against-alert winner). So 'direction accuracy' here means deciding WHEN a burst continues, plus vetoes (FlashGold, hold, drift). Cites: SpeedAlert_FlashGold_Micro.mq5:2639-2646, 2742-2767; re-derived in score_lattice.py.
- WHETHER. A serial stack is re-evaluated on EVERY tick while an alert is active; any veto sets speedActive=false and the alert re-fires on the next tick if the 10-s move still qualifies (replay Nov 2026, shipped: 146,251 alert starts for 26,502 independent episodes). Order: spread cap -> score winner -> body-against-stop rule -> FlashGold zone (decision tick, again at hold release, twice more in PlaceAction) -> entry hold (1,100 ms, then mid move >= +5 pts; a failed hold blocks new holds for the rest of the M1 bar) -> prior-60-minute drift sign -> burst gate (off) -> per-scenario caps -> continuation/tape filter at OrderSend -> the stop order must fill within 5 s. Calibrated preset, replay Nov 2026 counters: 106,090 decision ticks (74,994 mixed, 27,515 spread-skipped), FlashGold blocks 1,560, holds armed 1,150 / failed 474, drift blocks 227, cap skips 87, tape blocks 13, 312 stop orders placed, 168 expired, 141 filled (Mar 2026: 543 placed, 295 filled; 504,186 of 555,483 decision ticks spread-skipped at a 17-pt median spread).
- FLASHGOLD is not a rare-event trend filter: it is an ATR-scaled breakout re-arming gate (RSI/TDI slope alignment on M1/M5/M15 + a close-to-close burst of >= 0.5 ATR on M5 bars) whose armed level and band define BUY / SELL / no-trade price areas; it fires a signal on 31-33% of M5 bars, flips area ~1,700 times a day, and 66-77% of the entries it passes trade the OPPOSITE side to its last signal. Full mechanics in flashgold_summary. Effect: calibrated PF 1.150 with the gate vs 1.053 without (n 1,234 vs 1,771); shipped 0.719 vs 0.706; no FG input lifts PF above 0.753 with n >= 2,000 at a shipped base, but wider band / larger entry distance lift the calibrated base to 1.24-1.27 on 619-867 trades (grid average 1.15 -> 1.20 for band 0.25 -> 1.0).
- ORDER FLOW enters only through ScoreOrderFlow (mq5:2463-2493): up to three terminal global-variable votes (FORCE_IMB, NEAR_IMB, BOOK_IMB; |v| >= 5.0 gives one +1.0 vote; >= 2 same-sign votes = flowDir) that change the score/edge, the market-route permission, the scenario labels and the :FA/:FD comment that exit rules read. Absent from the replay and the tester. Only live evidence = the 2,584 real trades: FA 1,609 (62.3%, PF 0.805), FD 409 (15.8%, PF 0.916), none 566 (21.9%, PF 0.853), and 1,911 (74.0%) took the market route FOLM, which under the shipped settings cannot occur without at least one flow vote (no-flow maximum score 4.5 < WeakFlowMarketMinScore 5.0).
- SENSITIVITY (calibrated base PF 1.150, 1,234 trades; one input at a time): entry hold OFF 1.005 (n 2,960); 60-min drift OFF 0.998 (n 1,843); FlashGold OFF 1.053 (n 1,771); EntryRouterMode 2 -> 0.965; MaxTrailingMultiplier 7.5 -> 0.816 (30 is a peak: 25 -> 1.053, 40 -> 1.042); MinDirectionScore <= 3.0 -> 1.069 (n 1,737); FG band 1.0 -> 1.268 (n 619); FG entry distance 1.0 -> 1.243 (n 867); micro-break lookback 60 s -> 1.180; spread cap 12 -> 1.175. DEAD or near-dead: MinScoreEdge, InpBurstThresholdPts (gate was off while varied), DowngradeNeutralSellMarketToStop, WeakFlowMarket*, MarketFollow37, InpUse1000msHold, Limit* (router 0), FG_InpMinutes/Seconds/Milliseconds/Bars/DriftBars (their modes were off), InpCPRequireCostCoverage, FG_InpMinAligned 0 = 1. Around the SHIPPED preset every direction input stays inside PF 0.64-0.78 (n >= 2,000).
- NOISE. A ~1,200-trade replay has a bootstrap SD of PF 0.093 (re-derived: 5-95% range 1.00-1.31; the 158-day block bootstrap gives the same). In the 384-set joint grid the rank correlation of PF between periods is 0.06 (Nov-Feb vs Mar-May) and 0.27 (to-May vs Oct-Nov). SpeedLookbackSeconds is jagged (2/3/5/7/10/15 s -> 1.004/1.072/0.939/0.936/1.150/0.935) and the calibrated preset was chosen with all three samples in view. Whole-EA PF therefore cannot rank small direction-rule changes; the supply of direction EVENTS is large by comparison: independent alert episodes per day 2,208 at the shipped threshold vs 150 at the calibrated one (Nov 2026, 12 days), 233 per day calibrated in Mar 2026 (27 days).
- EXECUTION COUPLING. The entry is a stop order (calibrated: 50 pts beyond ask/bid, 5 s life, median 1.3 s from placement to fill), so direction only counts if price continues: 141 of 312 orders filled in Nov 2026, 295 of 543 in Mar 2026. EA-side exits, including the post-entry validation (the only post-fill direction re-check), are locked until the trade has first been > 6.8 pips (68 pts) in profit (hard-coded constant, mq5:12193-12202), so a wrong-way entry can only end at the broker stop or trailing. Entry hold, pending expiry and stop distance are therefore part of the direction confirmation chain and cannot be tuned independently of it.
- FIDELITY CAVEATS. (a) PARENT_EA_SOURCE.txt (header 1.499; ORIGIN.json calls the parent 1.500) differs from the micro EA only in version, TradingEnabled default, tester-only OnInit guard and one FlashGoldCaptureMicroQuote() call, so the direction logic is the live logic. (b) But the 2,584 real trades came from the older embedded build SpeedAlert_FlashGold_Embedded (saved chart header; it has no FG_InpBandAtr / FG_InpAgainst), so the v1.2 gate has no live validation. (c) The replay uses closed-bar parent/zone values (the EA keeps intrabar 'observed live' commits that depend on when the gate was called), nominal M5 bar ends (no quote-session calendar), CandleIndexToCheck 0 only and FIXED alert thresholds only. (d) The micro presets as shipped block after 4,096 occupied buckets (0 trades; the replay needs X_MicroRestart=1). (e) The shipped presets have TradingEnabled=false (the tester needs true) and v1.501 runs only in the Strategy Tester.
- STRUCTURAL BIASES. The candle-body vote mixes the MID close with the BID-based candle open (+spread/2, about +4.9 pts at the replay's 10-pt trigger spread, +6.6 at 13). ### The FlashGold direction filter, in detail

PROVENANCE. Literal MQL5 port of the Pine v6 'FlashGold Direction Filter v1.2' (core reference SHA256 387f49dc...), files FlashGold/DirectionFilterCore.mqh and DirectionFilterClock.mqh, wired in by SpeedAlertFlashGoldPermission.mqh. The EA asks it one question per tick: FlashGoldAllowsEntry(side, tick). It is a stateful per-bar SIGNAL generator plus a price-AREA gate.

1) SERIES (computed per filter bar; shipped native mode = M5 bars built from BID, FG_InpTf=5).
- ATR(14): Wilder RMA of true range seeded with the SMA of the first 14 true ranges (length hard-coded).
- TDI direction of a timeframe = sign of the slope of fast = SMA(RSI(close, 14 Wilder), 2): +1 rising, -1 falling, 0 equal (1e-10 tolerance), 99 = not enough history.
- Parent direction = TDI direction of FG_InpParentTf (M5) at the filter bar's close. Children Z1..Z6 (active: Z1 M1, Z2 M5, Z3 M15; Z4 H8, Z5 M1, Z6 M2 off) are the TDI directions of their timeframes (children longer than the filter TF use the previous COMPLETED bar when FG_InpHtfClosed; same or shorter TFs use the bar that closed at the filter bar's end). Because parent TF = Z2 TF = filter TF, Z2 always equals the parent, so FG_InpMinAligned 0 and 1 are identical in the sweeps and 2 really means 'M1 or M15 also agrees'.
- zoneBuy = parent == +1 and aligned >= min(MinAligned, active children); zoneSell = parent == -1 and the same; parent 0 only passes with FG_InpFlatParent; FG_InpUseZones=false makes zones always ready.
- burst = close(i) - close(i-1) in points (bid/ask are built as close -/+ FG_InpSpreadPts*tick/2, so the spread cancels); threshold = FG_InpBurstAtr (0.5) x ATR in points (FG_InpDistUnit=Points uses FG_InpBurstPts). BUY signal on bar i = zoneBuy and burst >= +threshold (and, if FG_InpUseDrift, close drift over FG_InpDriftBars > 0); SELL mirrored. FG_InpAnyCombo=true replaces the burst requirement by 'burst or parent already agrees' (FG_InpUseBurst then matters). FG_InpHoldBars > 0 adds a confirmation hold; 0 fires at once.
- On a signal: armedAt = bar END time, armedBar = i, armedDir = +/-1, armedAtr = ATR(i), armedPrice = signal entry price in level mode 0 (BUY: ask + FG_InpEntryDistAtr (0.25) x ATR; SELL: bid - 0.25 x ATR; ask/bid = close +/- FG_InpSpreadPts (25) / 2 = +/-12.5 pts); level mode 1 uses the bar close. The armed state is carried forward bar by bar until the next signal (FG_InpLast=0, shipped); other modes close the window after FG_InpMinutes, FG_InpBars filter bars, or an absolute FG_InpSeconds / FG_InpMilliseconds deadline after armedAt.
- Replay statistics (re-derived, Dukascopy-mid feed, bid bars): signals on 32.8% of M5 bars in Nov 2026 (905 of 2,760; about 75 a day; ATR(14) median 426 pts) and 30.9% in Mar 2026 (1,885 of 6,096; ATR median 825 pts); median 2 bars between signals.

2) GATE (per tick). band = FG_InpBandAtr (0.25) x armedAtr; upper = ceil((armedPrice + band)/tick) x tick, lower = floor((armedPrice - band)/tick) x tick (tick 0.01). BUY area <=> price > upper + tick/2; SELL area <=> price < lower - tick/2; in between = no-trade band (width 2 x band, median 218 pts in Nov 2026; with band 0 the test is price vs armedPrice and the signal bar is treated specially). Price = current BID in Tick check mode (FG_InpCheck=0). buyOK = open && FG_InpAllowBuy && inUp && (FG_InpAgainst || armedDir > 0); sellOK = open && FG_InpAllowSell && inDn && (FG_InpAgainst || armedDir < 0); zone = +1 / -1 / 0 (2 when the filter is disabled); 'open' = armed (mode 0) or inside the minutes/candles window. Per chart bar the core also returns armed, onSigBar, sigOk, newSignal, ended, expired, displayOpen, band, upper, lower (the EA reads only open and zone of the newest chart bar). In Tick mode the gate reads the armed state after the last COMPLETED filter bar (FgfChartPick picks the previous filter bar; the bar forming now is never used), so permission changes only when price crosses a band edge or a filter bar closes with a new signal. With FG_InpAgainst=true a BUY signal's level also defines a SELL area below it and vice versa; with false only continuation of the last signal is tradable (shipped sweep: n 4,287 vs 9,282, PF 0.752 vs 0.719; calibrated n 761, PF 1.134 vs 1.150).
- Replay statistics: gate in BUY area / SELL area / no-trade for 30.7 / 46.9 / 22.4% of seconds in Nov 2026 (24.7 / 48.1 / 27.1% in Mar 2026), about 1,700 area changes a day, median dwell 5 s. At the FIRST tick of an alert episode the zone agrees with the alert direction in 45.5% (shipped, Nov 2026), 55.3% (calibrated, Nov) and 52.3% (calibrated, Mar), is the no-trade band in 25.5 / 20.0 / 25.0% and points against the alert in 29.0 / 24.7 / 22.8%. Among the entries it passes at that tick, 77% (shipped Nov, 3,630 of 4,707) and 66% (calibrated Nov, 362 of 545) are on the OPPOSITE side to the last FlashGold signal (price has come back through its level); the rest continue it. Blocked winners are mostly alerts in the SAME direction as the last signal whose price is still inside the band (75% in shipped Nov). Trades by state: shipped stop entries continuing the last signal PF 0.817 (n 3,003) vs reversal 0.750 (n 3,409); fades 0.589 either way (n 2,829); calibrated continuation 1.125 (n 761) vs reversal 1.187 (n 475), buys 1.49 vs sells 0.97; PF by distance beyond the level in ATR quartiles 1.12 / 1.08 / 1.17 / 1.22 (calibrated), 0.76 / 0.74 / 0.82 / 0.80 (shipped stops): all within noise.

3) HOW THE EA USES IT. FlashGoldAllowsEntry(side) = gate[newest M1 chart bar].open && zone == side, where side is the side of the ORDER (a fade's own side). It runs on the M1 chart (FGV12_Update iterates chart bars), at the decision tick, at hold release and twice in PlaceAction. A refusal ends the alert (it re-fires next tick if the burst persists). The stale-level effect matters: with sparse signals the armed level can be old, and the gate then behaves like 'price above / below some earlier price', a slow side bias.

4) MICRO MODE (FG_Resolution=1). Filter bars are occupied buckets of the callback-observed BID (FG_IntervalMs 1000 shipped, 250 in Micro250ms); the first bucket of each epoch is dropped; no empty bars; a bar closes when a later bucket arrives; warm-up FG_MicroWarmupBars=100 occupied buckets; at most FG_MicroMaxBars=4096 per epoch, then the stream blocks until the EA restarts (68 min at 1 s, 17 min at 250 ms); a quote gap > FG_MicroMaxGapMs (60 s) starts a new epoch. Parent and zones stay native: each micro bucket reads the last native bar CLOSED at its open (no request-time look). ATR(14), burst, drift, hold and the candle window all count micro bars, so ATR is a ~14-second range and signals / area flips are far more frequent. FG_InpLast modes 3 / 4 (seconds / ms) apply an absolute deadline after armedAt (5,195 trades at 5 s, 343 at 500 ms in the sweep, PF 0.708 / 0.823). Replay with restart at capacity (X_MicroRestart=1): PF 0.713 shipped (9,111 trades); as shipped 0 trades (X_MicroRestart=0). FG_IntervalMs 100-60,000 ms gave PF 0.689-0.746 (best 15 s).

5) CALIBRATION STRUCTURE (see fg_key / FilterSeries in tools/flashgold.py). Inputs that change the SERIES (armedAt, armedBar, armedPrice, armedDir, armedAtr per bar) and force a rebuild: UseFlashGoldDirectionFilter, FG_Resolution, FG_IntervalMs, FG_MicroMaxBars, FG_MicroMaxGapMs, FG_InpTf, FG_InpLvMode, FG_InpSpreadPts, FG_InpEntryDistPts / FG_InpEntryDistAtr, FG_InpHoldBars / HoldFavPts / HoldFavAtr, FG_InpOnePerBar, FG_InpDistUnit, FG_InpBurstAtr / BurstPts, FG_InpUseBurst, FG_InpAnyCombo, FG_InpDriftBars, FG_InpUseDrift, FG_InpUseZones, FG_InpParentTf, FG_InpRsiLen, FG_InpFastLen, FG_InpMinAligned, FG_InpFlatParent, FG_InpIgnoreNa, FG_InpHtfClosed, FG_InpUseZ1-6, FG_InpZTf1-6, X_MicroRestart. GATE-ONLY inputs, re-evaluable per tick from stored (armedPrice, armedAtr, armedDir, armedAt, bar index, price) without rebuilding anything: FG_InpBandAtr, FG_InpAgainst, FG_InpAllowBuy, FG_InpAllowSell, FG_InpLast, FG_InpMinutes, FG_InpBars, FG_InpSeconds, FG_InpMilliseconds, FG_MicroWarmupBars. Not replayed: FG_InpCheck (Tick only), the intrabar 'observed live' parent/zone commits (the EA's native signal history depends on when the gate was called; the replay uses closed-bar values), the quote-session calendar for bar ends. For a labelled-dataset calibration the needed per-decision features are: order side, alert direction, armedDir, (price - armedPrice)/armedAtr, armedAtr, armedAt age, and the parent / child TDI directions at the signal bar; the gate-only inputs are then free to sweep, the series inputs need a signal-time recomputation (cheap in native M5: ~2,800 bars a month; heavy in micro mode: ~1 million buckets a month).

1. ## 3. Can the feed be rebuilt from prices? (no)

- LABEL SEMANTICS AND WHAT A MARKET ENTRY IMPLIES (verified in SpeedAlert_FlashGold_Micro.mq5; PARENT_EA_SOURCE.txt has byte-identical ScoreOrderFlow, AddFlowVote, WinnerSide, DecideAction, MarketEntryAllowedByFlow, ShortComment, ArmEntryHold, ProcessArmedEntryHold, BuildDirectionState, PlaceAction): ScoreOrderFlow 2463-2493 + AddFlowVote 2556-2570: each of FORCE/NEAR/BOOK with |v| >= 5.0 (line 251) is a buy/sell vote worth +1.0 score; 2 of 3 agreeing gives flowDir +-1, else 0; OK<0.5 or age>4000 ms gives no votes at all. :FA/:FD compare flowDir with the score WINNER (BuildDirectionState 2345-2346, ShortComment 3140-3141), not with the trade side (they coincide only for market and stop-with-burst entries; limit fades are excluded here). Enumerating the rules (verify_flow_label_algebra.py, 243 states per side) for MARKET entries: every market entry has >= 1 vote with the trade; :FD <=> exactly 1 vote with + 2 against AND M1 body + micro-break with the trade; no label <=> buys only (SELL with neutral flow is downgraded to a stop, DowngradeNeutralSellMarketToStop line 254), exactly 1 vote with, body + micro with the trade; :FA <=> >= 2 votes with (any price state); a stale feed can never give a market entry; with zero votes even body+micro+speed+spread scores 4.5 < WeakFlowMarketMinScore 5.0 and routes to a stop, so the feed is what unlocks the market route (74.0% of the real trades). The data agree: SM+none 0 of 965, BM+none 132 of 946 (14.0%), M1 body >= 21 pts held in 80 of 80 'none' entries (Wilson lower bound 95.4%).
- TIMING (changes how any proxy must be built): the account runs InpUseEntryHold=true, InpEntryHoldMs=1100 (saved-chart inputs; FlashGold_NativeReference_DISABLED.set lines 131-133; source default false/1000 at lines 276-277). ### Conclusion

(a) Deterministic proxy: NOT feasible. No feature, window, anchor or combination reproduces the verdict (best out-of-sample AUC 0.54-0.59 against ~0.9 needed; best 3-class rule = always agrees). (b) Stochastic label model conditional on quote features: not feasible in any useful sense: every ridge-logistic, hour-of-day and label-history model leaves log-loss within -4.2% .. +1.4% of the base rate with CIs including 0. What IS feasible and needed is a stochastic model of the three imbalance numbers themselves, with the label emerging from the EA's own rules, because the rules fix which labels a market entry can carry (FD only as 1 with / 2 against votes with body+micro; none only on buys with 1 vote; FA with >= 2 votes; no market entry without a live feed). (c) The feed behaves as unpredictable from broker/Dukascopy quotes at the resolution of these data (1 s stamps, selected sample, 155 minority labels): the single reproducible association (2-3 s momentum lower when the feed agrees, AUC 0.41) is a selection artefact of the weak-flow gate and vanishes inside the gate-satisfying subset (0.47 [0.42, 0.53]); the feed's absolute buy/sell verdict does not predict the next 5-30 s mid move; the label does not predict a better outcome (agrees minus disagrees -9.6 [-26.3, +7.3] realised points, realised sign flips between buys and sells but the label-independent forward move does not). Only the unselected numeric logs (force/near/book at every decision, SKIPs included) could prove or disprove predictability in the population. Practical consequence for the brief: do not ask for a price-derived proxy; ask for an exogenous, seeded vote generator, calibrate it to the observed route/label tables, evaluate every direction-logic candidate over many seeds and over bounding flow regimes, and request the live logs.

### Caveats

- Conditional sample: labels exist only for trades that passed score, route, entry hold and all gates, and the flow votes themselves feed the score and the route; FD and none additionally require body AND micro-break (enumerated and visible in the data). Within-sample associations are partly structural and the unconditional feed-price relation cannot be measured from these labels.
- Timing: stamps are floor seconds (+-0.5 s) and the label is frozen at hold arming (>= 1.1 s + first tick + ~150 ms before the fill); anchors lit/rel/arm are estimates, Dukascopy tick times differ from the broker's by an unknown amount, and for stop orders the decision is further away (hold + up to 5 s pending life).
- Different feeds: Dukascopy (median spread 64 pts, ~4.3 ticks/s in the 10 s before entries) is not the broker stream the EA and the external program saw (spread 12-15 pts per REPORT.md); quote-update features measured on the broker's own ticks in the tester may behave differently. Body and micro-break proxies are only approximate (micro-break is exact only at the decision tick).
- Coverage and power: only 1,260 of 1,911 market entries (66%) have ticks, hours chosen by trade count, 144 hour-clusters, 19 days, 155 disagrees, 80 none (BM only). Null SE of an AUC is 0.025 / 0.035; 'no proxy' means none above ~0.6, not exactly 0.5 (planted AUC 0.54-0.59 is not reliably recovered).
- Multiplicity and CI scope: 348 strongly correlated candidates (66 outside 0.5 +- 1.96 SE, family-wise permutation p = 0.043 with rows treated as independent); nested-metric CIs hold the selection fixed (slightly narrow); clusters are UTC hours; 'best of 8 variants' ridge AUC 0.586 is selected on label AUC.
- Quote sizes are quantised and absent from MqlTick; data/hf behaves similarly (check_hf_sizes.py) but with a different ask/bid size correlation (0.72 vs 0.05), so the two copies are not processed identically.
- Outcome analyses: realised points include slippage and label-dependent exits (:FD defensive exits) and a market that fell 7.2% over the window; the buy/sell sign flip of FA minus FD (+16.3 vs -30.1 pts) is not reproduced by the label-independent forward move and has multiplicity (several splits); forward moves are measured from the stamped second + 0.5 s on Dukascopy mid.
- Unknowns I could not determine: the numeric scale, update cadence and venues of FORCE/NEAR/BOOK (the 5.0 threshold's position in their distribution), whether MT5 tester ticks carry last/volume for this broker, the exact decision time of each trade, whether the live account used the chart inputs unchanged for the whole window (assumed), and the unconditional price->flow relation.
- Label persistence is real but weak (P(next label same) 0.685 vs 0.648-0.672, p=0.001; hour-of-day p=0.011; day p=0.27) and its out-of-sample predictive value is AUC ~0.56; the vote-generator calibration values quoted above assume independent components and an assumed body+micro share, so they are seeds, not results.
- Repository note: REPORT.md, REPORT.template.md and tools/make_report.py show uncommitted edits made at 16:08 UTC by another actor, not by this probe (this work only read the repo; REPORT.md now also says the label does not tell the result reliably, with the same buy/sell sign flip). ## 4. Engine changes and the calibration inner loop

- Re-running the engine is cheap, so offline re-scoring is a screening tool, not the main loop. Measured on the 4,383,562-tick month 2026-11, 2 threads, steady state: 0.19 s (shipped alert x7.5) and 0.03 s (calibrated x30) per replay; results/queue.log gives 316 full-feed replays in 531 s and 48 in 49 s, i.e. about 1.0 to 1.7 s per replay of all 62,732,047 ticks on 4 cores. Idle skipping via Sim._cand (sim.py:48-59) must stay: candidate ticks are 0.53% (x30) to 20.0% (x7.5) of ticks, yet the engine evaluates the direction state (C_DECISIONS, engine.py:1049) on 1.80M ticks (x30), 20.69M (x7.5, 33% of ticks) and 42.09M (x3), summed over the 9 months. Offline re-scoring only pays above roughly 1e5 input sets.
- Order flow touches the engine in exactly two ways. (a) One read per direction evaluation: EA BuildDirectionState 2339-2342, ScoreOrderFlow 2463-2493, AddFlowVote 2556-2569. (b) A per-order label ':FA'/':FD' (EA ShortComment 3140-3141) that four exit branches read later (EA 11218-11262 stop-flow danger close, 10900-10906 V40 pre-speed shield, 10921-10927 FOLM danger loss, 10948-10953 immediate-by-flow) plus MarketEntryAllowedByFlow (2770-2789), BlockStrongFlowAgainst (2748) and the scenario keys BFNF/FLXQ/BFNO/BFA (3159-3186). The change is four per-chunk arrays (fl_ix int32[n_ticks], fl_t int64, fl_ok uint8, fl_v float64[n,3]), about 25 lines at decision time and one label array per order table; empty arrays or UseOrderFlow=false means neutral. Because flow is read only on ticks the engine already processes, idle skipping is untouched. Scratch prototype: neutral-flow output is bit-identical to the current engine (all 18 trade columns, all 21 counters) for 5 presets on 2026-11.
- The 11 flow inputs missing from engine.NAMES must be added: UseOrderFlow, MaxFlowAgeMs, MinFlowImbalance, FlowComponentScore, BlockStrongFlowAgainst, FlowDisagreeMakesDefenseImmediate, FOLMFlowDisagreeDangerLossPoints, UseStopFlowDisagreeDangerClose, StopFlowDisagreeDangerLossPoints, StopFlowDisagreeDangerMinHoldMs, StopFlowDisagreeDangerNeedsOppositePressure (results/inputs_classification.csv lists them as 'no effect in the tester'). - The engine re-evaluates direction on every tick of an alert window and the first passing tick enters, so the direction logic is a first-passage detector: per-tick noise in a flow series is a multiple-comparison lottery. A toy 1 Hz momentum-coupled series took the shipped preset from 545 to 1,006 trades in 2026-11 (labels FA 414 / FD 45 / none 547). Cost 4.2 us per row (1.99 s vs 0.19 s per month, about 10x a plain replay) and 288 B per row (58 int32 + 14 float32). Full-feed volumes at 288 B/row: 1.80M rows = 0.52 GB at x30, 20.69M rows = 5.96 GB at x7.5, so write per chunk and never hold the log. ### Flow series design

Per chunk (one weekly chunk of the Feed, indexed like feed.t[a:b]), four arrays, all C-contiguous and writable (read-only or mmap arrays make numba compile a second specialisation): fl_ix int32[n_ticks] = index of the last published update at or before tick i (-1 = none yet; this is the alignment array, O(1) lookup, same pattern as idxL), fl_t int64[nu] = heartbeat / publication time in feed ms (strictly increasing), fl_ok uint8[nu] = the feed's OK flag, fl_v float64[nu,3] = FORCE_IMB, NEAR_IMB, BOOK_IMB as published (synthetic values quantised to 1/8 so float32 copies in the log and threshold ties are exact). Neutral flow = empty arrays (shapes (0,), (0,), (0,), (0,3)) or UseOrderFlow = 0. Freshness model for MaxFlowAgeMs: at decision tick i, k = fl_ix[i]; fresh = k >= 0 and fl_ok[k] != 0 and (T[i] - fl_t[k]) <= MaxFlowAgeMs. Outages are modelled by gaps in fl_t or fl_ok = 0, so the same code path gives 'stale'. Publication lag is modelled by shifting fl_t later than the information time, never earlier. The engine reads the series only at the direction evaluation (engine.py:1113) and at no other tick, and then carries the label fl_lab = +1 (FA) / -1 (FD) / 0 on the pending, market and position tables; the entry-hold path restores the label stored at the arm tick (hold_fl).\n\nBuild and cache: tools/flowsim.py with spec = {model: 'neutral'|'tape'|'lead'|'replay', period_ms: 1000, lag_ms: 0, seed, quant: 0.125, scales / information coefficient, dropout: {p_outage, mean_ms}} (JSON-able; flow_key(spec) mirrors flashgold.fg_key). 'tape' = contemporaneous series from the last 1-3 s of mid moves plus noise; 'lead' = adds a controlled share of FUTURE return (look-ahead by construction, label results as upper bounds); 'replay' = piecewise-constant series from the owner's live CSV samples. FlowSeries(feed, spec).chunk(c) builds lazily with np.random.default_rng([seed, chunk_start_ms]) (deterministic, independent of thread order), vectorised over the update grid: grid = np.arange(t0, t_end+1, period); j = np.searchsorted(t, grid, 'right') - 1; ret = (mid[j] - mid[j3]) / 0.01 ...; values = np.round(v * 8) / 8; fl_ix = (np.searchsorted(grid, t, 'right') - 1).astype(np.int32). Sim keeps a dict of at most 2 FlowSeries keyed by flow_key (like fg_cache at sim.py:35) and Sim.run prebuilds every chunk in the calling thread before pool.map; optional disk cache in data/cache/ (already in .gitignore) as npz keyed by hash(spec, feed identity). Prototype numbers: 1 Hz = 58-72 ns/tick and 10.5-10.8 B/tick (0.54 s and 99 MB for the 9.24M-tick month 2026-03), 4 Hz = 144 ns/tick and 30-31 B/tick.\n\nEngine lookup (prototype, passes the parity tests):\nuse_flow = P[I_UseOrderFlow] > 0.5 and len(fl_ix) > 0\n...\nif use_flow:\n    fl_k = fl_ix[i]\n    if fl_k >= 0 and fl_ok[fl_k] != 0 and (t - fl_t[fl_k]) <= P[I_MaxFlowAgeMs]:\n        fl_fresh = True\n        for q in range(3):\n            v = fl_v[fl_k, q]\n            if abs(v) >= P[I_MinFlowImbalance]:\n                if v > 0.0: vb += 1; buy += P[I_FlowComponentScore]\n                else: vs += 1; sell += P[I_FlowComponentScore]\n        fl_dir = 1 if vb >= 2 else (-1 if vs >= 2 else 0)\nThen fa/fd after the winner, BlockStrongFlowAgainst after the spread skip, neutral/weak market gating, scenario keys and the four exits as listed in the insertion points. Verified in the prototype: UseOrderFlow = 0 with a series present equals the neutral run bit for bit; BlockStrongFlowAgainst = 1 gives 25,872 skip_flow_block rows with the toy series; R_STOP_FLOW fires; scenarios FLXQ/FOLM/EXHL/CONT/BNO appear with FA/FD labels (BFNF/BFNO/BFA depend on the series).

### Risks

- The synthetic feed is not the real feed: scale, cadence and predictive content are unknown, and the real labels (FA agrees with the worse trades: PF 0.80 vs 0.92) suggest flow is contemporaneous with the burst rather than predictive. Treat results as sensitivity analysis over an information coefficient, fit the generator to the live CSV logs (marginals, update cadence, freshness duty cycle, FA/FD/none 62/16/22%, FA share of FOLM 80%), and label any 'lead' model as an upper bound.
- First-passage lottery: per-tick evaluation inside 20 s windows multiplies any noise (toy series: 545 -> 1,006 trades). The Dukascopy-based replay has 4.5 ticks/s on average and 7.8 ticks/s at candidate ticks, which need not match the broker's evaluations per window; entry counts and first-pass timing will not transfer 1:1 to live.
- Look-ahead leakage: features must only use ticks <= i and flow published at or before the tick; forward outcomes are labels only. Add a truncation test (cut the feed after tick i and require identical logged features at row i).
- Engine/scorer drift: two implementations of the same scoring. Mitigate with shared njit kernels (_fg_z and the log helpers) and the master parity test (re-score at theta0 and at theta' equals engine on 100% of shared rows). Never store float32 copies of values later compared with inputs (mfe/mae and CP stats are float32 in the prototype and matched on 15 variants, but ties are a latent risk: store indices or float64).
- Censoring and path state (see limits): using a theta0 log to rank distant thetas is biased; only signal-only replays or full replays are exact for search.
- Overfitting and multiple testing: a search over 1e5 to 1e7 input sets on about 1,200-trade samples; the REPORT already found rank correlation 0.06 between calibration and validation profit factor of neighbouring sets and a hold-out that is no longer clean. Forward-outcome metrics over thousands of signals are less noisy than trade profit factor but need nested validation and a count of effective trials.
- Fill-model dependence: forward labels inherit the 150 ms delay, 10 point snap and stop-loss slip factor 1.5 (fitted on one month of real fills); compute labels for factors 1.0 / 1.5 / 2.0 and require the ranking to be stable.
- Numba: any run_chunk signature, dtype or readonly change recompiles (about 44 s); keep arrays int32/int64/uint8/float64 C-contiguous and writable; a variable first assigned inside a branch must be initialised before it (fl_lab, sig_ms); silent truncation limits (20,000 trades per chunk at sim.py:72, MAXP/MAXO = 12) need assertions, plus log_rows_dropped == 0.
- Latent Sim._cand race (sim.py:48-59 called from worker threads, clear() above 400 entries): fix when adding the flow cache.
- Per-month feeds cut weekly chunks (9,241 vs 9,282 shipped-preset trades); never mix per-month and whole-feed numbers in one comparison.
- The four flow-dependent exits are unvalidated (no real occurrences, rare in replay); implement exactly from EA 10888-10990 and 11218-11262 with forced-state unit tests, and do not let them drive calibration.
- Memory: whole feed 7 GB + idx cache 0.5 GB per lookback + flow 0.67 to 1.9 GB + log chunks; the union table at x7.5 would be 9.7 GB on disk; run_all.sh's rule of one feed-loading process at a time must stay.

It is concentrated in: buys (+44.5, t 4.8; sells +17.7, t 2.4, but net -2.5 because sells cost 20.2 vs 15.8); FLXQ:BS +44.2 (t 3.8) and QUAL:BS/SS +45.0/+33.7 (t 2.9/2.6) but not FLXQ:SS (+7.3, t 0.9; -1.6 and -1.0 in validation and hold-out); bursts of 150-400 pts (+30..+38, t 2.0-3.5) and >=600 pts (+81, t 3.0, n 93) but not 400-600 (+9) or 100-150 (-33); spread <=13 at order (+31..+36, t 1.8-3.4) vs 14-16 (+12.5, t 1.3); and four months (Jan, Feb, Mar, Nov 2026: +37..+50, t 2.0-2.8) while the other five are about 0 (-0.3..+11). The FlashGold gate adds direction information in this regime: trades the gate keeps average +31.3 gross (t 5.2), trades taken only without it +7.0 (t 1.0), difference 24.3 +/- 9.2. NO SKILL in: the shipped preset overall (gross +0.7 +/- 1.2, t 0.6; MFE excess -3.7/-0.8/+0.8/-1.4 pts at 10/30/60/100 against a no-skill reference; zero in every split, side and month; its only exception is alerts >=600 pts: n 219, gross +34.8, t 3.2); its EXHL limit fades (-1.2 / -5.2, t -0.4 / -2.0; the market keeps going against them); its FlashGold gate (gross +0.7 on vs +0.1 off); the real account's flow label (disagrees minus agrees +5.7 pts, CI -5.4..+16.7; FOLM re-managed MFE excess +1.4/+1.5/+1.8/+0.2); hour of day or session (rank correlation of hourly mean points between splits -0.3..+0.3 in both replays). Caveats: the calibrated preset was chosen with all three splits in view; costs swing 3x by month (stop-loss slip mean 7-9 pts Oct-Nov 2026 vs 22-37 pts Jan-Mar 2026) and the cost model was fitted on one month of real fills; the replay cannot take the flow-driven market route that made 74% of the real trades; real trades carry no MFE; June-Sep 2026 is missing.

### Design implications

- Do not justify the event table by replay speed: a 9-month engine replay is 0.3 s (calibrated-style) to 2.2 s (shipped-style) warm, so 1,000 candidates cost 5-37 minutes. The table pays from about 10^4-10^5 candidates (joint search over 10+ weights and thresholds): numba re-scoring is 30-90x faster than a replay, numpy only 1-3x (about 2 s per candidate over a shipped-style 20.7M-row table, equal to the replay).
- Decide what the table is for: (a) an execution-independent direction objective (forward mid move at 1-60 s and max up/down within 30/60 s, signed by the chosen side; metrics gross mid-to-mid edge and MFE-excess-over-no-skill) and (b) a cheap pre-screen; always confirm finalists in the full replay (0.3-2.2 s). Stops, trailing and order types stay out of the objective and are calibrated by hand.
- Build it month by month with the engine's own decision branch (logging-only patch; trades and counters identical in all 18 month runs; scratch copy in events-baseline/xtools, built by make_patched.py): one row per C_DECISIONS evaluation at the lowest alert multiplier of interest (x7.5: 20.7M rows) or only x>=20 (about 2M rows); keep alert size in spreads as a column so thresholds re-apply offline; cost about 1.8 s per million rows and 2.3 GB peak per 4.3M-row month; add an episode id and weight by episode (1 to 151,484 rows per episode).
- Store integer-valued features (points x2 as int16, spread as integer points) and reproduce the engine's tie rules (spread <= cap, body >= 21, micro > buffer): float32 storage made 0.03-3% of rows disagree, all at exact thresholds, and 6% of the calibrated preset's decision rows sit exactly at the 14-point cap. The replay's rebuilt quotes make those ties float-noise decisions; the live EA has its own noise from broker doubles.
- The replay has no direction choice beyond with-the-burst or skip (winner equals burst direction in 100% of rows with a winner; against-burst trades come only from the EXHL fade). The order-flow simulator creates every other direction decision (up to +3.0 of votes, market route FOLM = 74% of real trades). Generate flow features per decision tick (23M shipped-style, 2M calibrated-style rows) or as per-tick float32 columns (250 MB per column for 62.7M ticks). The engine's npz store holds only t/bid/ask; the Hugging Face parquet (Nov 2025-May 2026) and the Dukascopy .bi5 files carry top-of-book bid/ask volume and would have to be re-extracted.
- Validate any simulated flow label against the real account before using it: 2,584 real trades carry FA/FD/none labels (1,609/409/566), FD rates per route are FOLM:SM 139/965 = 14% and FOLM:BM 113/946 = 12%, the label did not predict outcomes (+5.7 pts, CI -5.4..+16.7), and 1,621 real entries lie inside downloaded ticks for a path check.
- Plan statistics around episodes and folds, not trades: SE of the mean gross edge is 5.8 pts for 1,236 calibrated trades (SD about 200), a 10-pt difference needs about 6,300 trades per arm; the data hold 17.8k x30 and 127k x7.5 alert episodes (the episode count depends on the merge gap: 311k at 5 s, 127k at 20 s, 43k at 60 s at x7.5). Use the three splits as nested folds, keep the hold-out untouched during the search (the calibrated preset has already seen it) and correct for the number of candidates searched.
- The bar to beat is concrete: shipped logic gross edge 0 (+0.7 +/- 1.2); calibrated entries +28.3 +/- 5.8 with total cost 18.5 vs the quote. A direction rule is better only if it raises gross edge (or MFE excess) on both buys and sells and in at least 4 of 9 months; sells (+17.7 vs +44.5 gross, 4 pts higher cost) and FLXQ:SS (about 0 outside the calibration months) are where the headroom is.
- FlashGold-gate calibration is the slow axis: a native M5 series costs 0.14-0.31 s per month per distinct FG configuration (2.1 s for nine months) and about 5 s per replay in micro mode (project log: 97 replays in 489 s). Precompute the gate state per decision row for a grid of FG configurations instead of rebuilding per candidate. Evidence it matters: kept-by-gate trades +31.3 gross vs +7.0 for trades only taken without it (calibrated); no effect for the shipped preset.
- Run settings for any new script: python -I -B, NUMBA_CACHE_DIR outside the repository (cold compile 34.3 s, cached load 0.15 s; the repository's tools/__pycache__ already holds a cache indexed at the current run_chunk line, I did not write to it), one month in memory at a time (0.6-1.0 GB), and the engine's cache keys: idx by lookback, candidates by (lookback, min points, multiplier), FilterSeries by FlashGold parameters.
